1. 연구 목적과 필요성

같은 보안 약점을 여러 제도가 따로 검사하게 하는 지금의 구조를 숫자로 보여 주고, 한 번의 시험 결과를 여러 제도에서 인정받는 길을 찾음 · 출처가 달린 전문은 docs/01_연구배경.md

문제
  • 국방 SW는 방위사업청 매뉴얼에 따라 신뢰성시험(코딩규칙, 취약점·보안약점, 메트릭, 동적시험)을 받음
  • 보안 영역에는 행안부 개발보안, K-RMF, KCMVP, 보안기능확인서·CC가 따로 있음
  • 제도마다 참조 표준과 목록이 달라 같은 결함을 여러 번 시험하고 소명함
A가 답할 질문
  • RQ1 제도마다 근거 법령, 소관 기관, 적용 대상, 참조 표준은 무엇인가
  • RQ4 겹침을 줄일 상호인정·통합 방안은 무엇이고, 해외는 어떻게 하는가
  • B의 정량 결과(RQ2·RQ3)를 받아 제언의 근거로 씀

3. 제도 프로파일 카드 (A2)

제도마다 같은 항목으로 카드를 만들어 나란히 견줄 수 있게 함. 아홉 개 제도 가운데 앞의 두 개가 정량 비교 대상이고 나머지는 제도 소개까지만 함

① 방사청 매뉴얼 SW 신뢰성시험 정량 비교

근거
「무기체계 소프트웨어 개발 및 관리 매뉴얼」 방위사업청 매뉴얼 제2024-6호(2024.12.26. 개정) 확인 표지 · 관련 문서로 「국방전력발전업무훈령」, 「방위사업관리규정」, 「무기체계 소프트웨어 개발 지원에 관한 규정」 등을 듦 확인 본문 3쪽. 훈령 원문은 확인 필요
소관
방위사업청(사업관리부서). 정적시험·보안성 시험은 연구개발주관기관(국방과학연구소, 업체)이 일차 실시하고 기술지원기관(국방과학연구소 정보화기술실, 국방신속획득기술연구원, 국방기술품질원, 국방기술진흥연구소)이 확인. 동적시험은 자체 또는 제3자 검증 뒤 기술지원기관 검토 확인 본문 3쪽·111쪽
대상
방위력개선사업으로 획득되는 SW. 부록 7은 무기체계 연구개발, 핵심기술(시험개발), 부품국산화(핵심부품), 경미한 성능개량 사업에 적용. 언어는 C, C++, Java, C#. 기개발·상용 SW는 수정 없이 재사용하면 제외 확인 본문 3쪽, 부록 7-2~7-3
시험 항목
신뢰성시험 = 정적시험(코딩규칙 검증, 취약점 점검, 소스코드 메트릭) + 동적시험(코드 실행률). 보안성 시험 = 전장관리정보체계에 한해 행안부 「소프트웨어 개발보안 가이드」 준수 여부를 국정원 CC 인증 도구로 확인 확인 본문 10~11쪽, 부록 7-4, 7-17
참조 표준
코딩규칙: MISRA-C 2012·2023, MISRA-C++ 2008·2023, C++ Core Guidelines, Oracle Java 코드 컨벤션, C# 컨벤션, .NET 가이드라인(부록 6-2). 취약점: CWE-658/659/660 세 뷰 + 보안약점 점검 목록 44개(부록 7-10~7-11). 참조 CWE 버전은 규정이 없고 시험확인서 양식 예시에만 "CWE-658(V4.10)"이 보임(부록 7 별지 2). 관련 문서에 ISO/IEC/IEEE 12207-2017 확인
채택 형태
해외 코딩 표준과 CWE 뷰를 참조하면서, 보안약점 44개 선정 목록과 동적시험 등급표(결함 영향도·빈도·제어 가능성 → 문장/분기/MC·DC)는 매뉴얼이 직접 정함 확인 부록 7-13~7-14. 소스코드 메트릭의 종류·제한값은 사업별로 연구개발주관기관이 제시해 검토회의에서 결정하며 매뉴얼에는 예시만 있음 확인 부록 7-12 (기획안의 "메트릭 한계값 = 국내 고유 기준" 표현은 수정)
상호인정
제도 안에서는 기개발 SW(신뢰성시험을 거쳤거나 규격화된 SW) 재사용 시 시험 제외, 변경 없으면 개발시험평가 때 정적·동적시험 생략 가능 확인 부록 7-3, 7-9, 7-16. 다른 제도(행안부 진단, CC, K-RMF 등)의 결과를 인정하는 조항은 본문·부록 7에서 찾지 못함. 보안성 시험이 행안부 가이드와 CC 인증 도구를 기준으로 삼는 것이 유일한 연결 고리

② 행안부 SW 개발보안 정량 비교

근거
전자정부법 시행령 제71조제1항(감리대상 사업) → 「행정기관 및 공공기관 정보시스템 구축·운영 지침」(행정안전부고시 제2021-3호) 제50조~제53조 → 「소프트웨어 개발보안 가이드」(행정안전부·KISA, 2021.11.) 확인 가이드 10쪽, 13쪽 표 2-1. 지침 조문 원문은 확인 필요
소관
행정안전부(지침·고시), 한국인터넷진흥원(가이드 발행). 진단은 감리법인이 국가보안기술연구소장이 인증한 진단도구로 수행하고 진단원을 우선 배치 확인 가이드 13쪽
대상
정보시스템 감리대상 사업(감리대상 밖 사업도 자체 적용). 신규개발은 설계 산출물과 소스코드 전체, 유지보수는 변경분. 상용 SW 제외 확인 가이드 13쪽
시험 항목
설계단계 보안설계 기준 20개, 구현단계 보안약점 제거 기준 49개. 감리기준 제10조 제1항 세부검사항목에 포함 확인 가이드 13쪽, 부록 342·348쪽
참조 표준
항목마다 참고자료로 MITRE CWE 번호를 적음(49개 항목 → CWE 61개, 1:N) 확인 가이드 4장 각 항목, B2 매핑
채택 형태
CWE를 항목별 참고 기준으로 쓰되 항목 선정과 분류(7개 유형)는 국내에서 정함. 2011년 제정 뒤 2013·2017·2019·2021년 개정 확인 가이드 제·개정 이력
상호인정
매뉴얼 ①의 보안성 시험이 이 가이드를 기준으로 삼음(전장관리정보체계). 반대로 이 가이드가 다른 제도 결과를 인정하는 규정은 가이드 본문에서 찾지 못함. 지침 원문 확인 뒤 확정 확인 필요

5. 해외 상호인정 사례 (A4)

한 번 받은 시험·인증 결과를 다른 나라나 다른 제도에서 그대로 인정하는 세 가지 방식을 견줌

사례무엇을 인정하나어떻게 작동하나우리 제도에 주는 시사점상태
CCRA (CC 국제상호인정협정) 가입국 인증기관이 발급한 CC 인증서 공통 평가기준(ISO/IEC 15408)과 공통 평가방법을 쓰고, 협력 보호프로파일(cPP) 기반 인증서를 가입국이 서로 인정함 기준과 방법을 먼저 통일해야 결과 인정이 가능함. 국내 제도 간에도 "공통 목록"이 먼저 필요함 인정 범위 확인
미국 RMF 상호인정 (reciprocity) 다른 기관이 수행한 보안통제 평가 결과 국방부·연방기관이 같은 NIST 통제 목록을 쓰고, 이미 평가된 결과를 재평가 없이 받아들이도록 정책으로 명시함 같은 통제 목록을 쓰는 것만으로는 부족하고, "재평가하지 않는다"는 규정이 따로 있어야 함 정책 문서 확인
DO-330 (항공 SW 도구 자격) 검증 도구 자체의 신뢰성 특정 인증 사업 안에서 그 사업의 용도와 도구 자격 등급(TQL)에 대해 도구 자격을 인정받음. 같은 용도·등급이면 변경 영향 분석만으로 다른 사업에 재사용할 수 있음 (독립된 "도구 인증서"는 아님) 검증된 도구·용도 목록을 두고, 재사용할 때 변경 영향 분석만 요구하는 형태가 현실적임. 도구 결과서를 그대로 인정하는 방식보다 좁음 원문 확인 FAA AC 20-115D

세 사례의 공통점 추정: 결과를 인정하기 전에 기준(목록), 방법(절차), 도구 가운데 적어도 하나를 먼저 통일했음. 제언 후보 ①②④가 이 세 축에 각각 대응함

6. 이해관계자 (A5)

제도를 바꾸려면 누가 결정하고 누가 영향을 받는지 알아야 함. 여덟 주체를 역할과 관심으로 나눔

7. 정책 제언 후보와 평가 틀 (A6)

네 가지 후보를 세 기준으로 평가함. 평가는 B의 정량 결과가 나온 뒤 채움

제언 후보내용법적 근거가 필요한가어느 기관이 조정하나비용 대비 효과필요한 근거
① 공통 CWE 핵심 목록매뉴얼 44개와 행안부 49개의 공통 항목을 핵심 목록으로 정해 두 제도가 함께 씀매뉴얼·가이드 개정 수준 추정방사청·행안부평가 전RQ2 겹침 크기(교집합, Jaccard)
② 시험 결과 상호인정한 제도의 시험 결과서를 다른 제도가 재시험 없이 인정인정 규정 신설 필요 추정국방부·방사청·국정원평가 전RQ3 1회 분석의 제도별 충족률, RMF reciprocity 사례
③ 기준 버전 현행화 주기CWE Top 25 등 참조 표준이 바뀔 때 국내 목록을 갱신하는 주기와 절차를 정함매뉴얼 개정 수준방사청평가 전제도별 참조 표준 버전 차이(A3 표)
④ 오탐 사유서 표준화·도구 검증오탐 소명 양식을 통일하고, 검증된 정적분석 도구·용도 목록을 두어 재사용 시 변경 영향 분석만 요구도구 검증은 규정 신설 추정방사청·국방기술품질원평가 전RQ3 오탐 표본, DO-330 사례
