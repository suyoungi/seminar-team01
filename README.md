## 왜 이 주제인가

국방 소프트웨어는 방위사업청의 「무기체계 소프트웨어 개발 및 관리 매뉴얼」에 따라 코딩규칙, 취약점, 소스코드 메트릭 등을 검사하는 신뢰성시험을 받습니다. 그런데 보안 쪽에는 행정안전부 SW 개발보안, 국방 사이버보안 위험관리(K-RMF), 암호모듈 검증(KCMVP), 보안기능확인서와 CC 인증처럼 비슷한 목적의 제도가 여럿 더 있습니다.

이 제도들은 저마다 국제표준이나 해외 기준을 가져다 쓰지만, 가져온 방식이 제각각입니다. 어떤 제도는 국제표준을 그대로 쓰고, 어떤 제도는 일부만 고쳐 쓰며, 어떤 항목은 국내에서 따로 만들었습니다. 그 결과 같은 결함을 두고 제도마다 다른 목록으로 검사를 요구하고, 한 제도에서 받은 시험 결과를 다른 제도에서는 인정하지 않습니다. 개발업체는 같은 코드를 여러 번 시험하고 여러 번 소명해야 합니다.

이 프로젝트는 "얼마나 겹치는지"를 감이 아니라 숫자로 보여 주고, 그 숫자를 근거로 제도를 손볼 방법을 제안합니다.

## 무엇을 밝히려 하는가

| RQ2 | 제도별 보안약점 요구 항목을 CWE 기준으로 맞추면 얼마나 겹치고 어디서 다른가 | 기술 담당 |
| RQ3 | 정적분석을 한 번 수행한 결과가 여러 제도의 요구를 동시에 채울 수 있는가 | 기술 담당 |
| RQ4 | 겹침을 줄이려면 어떤 상호인정·통합 방안이 가능하고, 해외 사례에서 무엇을 배울 수 있는가 | 정책 담당 |

## 어떻게 진행하는가

프로젝트는 세 갈래로 나뉘고, 마지막에 하나로 합칩니다.

**1. 제도 분석 (정책 담당)**
법령과 매뉴얼, 가이드를 읽고 제도마다 "제도 카드"를 만듭니다. 카드에는 근거 법령, 소관 기관, 적용 대상, 시험 항목, 참조 표준, 표준을 가져온 방식(그대로 채택 / 고쳐서 채택 / 일부만 채택 / 국내 추가)을 적습니다. CC 국제상호인정(CCRA), 미국 RMF 상호인정처럼 해외에서 시험 결과를 서로 인정하는 사례도 함께 조사합니다.

**2. 기준 대조 (기술 담당)**
방위사업청 매뉴얼의 보안약점 44개와 행정안전부 가이드의 49개 항목을 모두 CWE 번호로 바꿉니다. 여기에 CWE Top 25를 더해 "CWE 번호 × 제도" 표를 만들고, 제도끼리 겹치는 항목 수, 유사도(Jaccard), 한 제도에만 있는 항목을 계산합니다. 결과는 벤 다이어그램과 히트맵으로 그립니다.

**3. 정적분석 실증 (기술 담당)**
NIST SARD의 Juliet 시험용 C/C++ 코드 가운데 위 CWE에 해당하는 것을 골라 cppcheck, clang-tidy, flawfinder 같은 공개 도구를 돌립니다. 도구가 어떤 CWE를 잡아내는지 세어, "한 번 분석하면 제도별로 몇 개 항목을 채우는지" 표로 만듭니다.

**4. 통합과 제언 (공동)**
2와 3의 숫자를 1의 제도 분석에 붙여 제언을 씁니다. 후보는 공통 CWE 핵심 목록 도입, 시험 결과 상호인정, 기준 버전 현행화 주기, 오탐 사유서와 도구 검증 제도이며, 각각 법적 근거가 필요한지, 어느 기관이 조정해야 하는지, 비용 대비 효과가 어떤지를 따집니다.

### 범위

- 포함: 무기체계 SW(중심), 비교를 위한 행정안전부 개발보안, C/C++ 코드
- 제도 소개만 하고 숫자 비교는 하지 않음: K-RMF, KCMVP, 보안기능확인서·CC, GS·DQ마크, DO-178C
- 제외: 비공개 문서, 실제 무기체계 소스코드, 실제 장비가 필요한 동적시험 실측

## 진행 단계

기간은 정하지 않고 순서만 정합니다. 각 단계는 앞 단계의 산출물이 나오면 시작합니다.

| 단계 | 정책 담당 | 기술 담당 | 함께 |
|---|---|---|---|
| 1 | 자료 확보, 매뉴얼 원문 입수 | CWE 목록 수집, 개발 환경 구성 | 기획안 확정 |
| 2 | 제도 카드 작성 | 44개·49개 항목 CWE 매핑 | 매핑 기준 합의 |
| 3 | 표준 채택 방식 분류 | 겹침 분석 스크립트 | |
| 4 | 해외 사례 조사 | 시각화, Juliet·도구 환경 구축 | 중간 연결 회의 |
| 5 | 이해관계자 분석 | 정적분석 실행·집계 | 중간 점검 |

| 7 | 보고서 통합, 서론·결론 | 데모·저장소 정리 | 교차 검토 |

## 저장소 구성 (예정)

```
seminar-team01/
├── README.md          이 문서
├── 기획안.md           기획안 전문
├── index.html         팀 페이지 (GitHub Pages)
├── briefing.html      제도 분석 브리핑 (팀원 A 작업분)
├── data/              CWE 목록, 제도별 매핑표 (CSV)
├── analysis/          겹침 분석 스크립트 (overlap.py 등)
├── static-analysis/   Juliet 케이스 선별, 도구 실행 스크립트, 결과표
├── figures/           벤 다이어그램, 히트맵
```

## 함께 일하는 방식

- main에는 PR을 거쳐 팀원 1명이 승인한 변경만 들어갑니다. main에 직접 푸시하면 거절됩니다.
- 할 일마다 브랜치를 만들고, 한 PR에는 한 가지 변경만 담습니다.
- 리뷰 의견은 위치, 관찰, 증거, 제안 순서로 씁니다.
- 주 1회 회의하고 회의록을 `docs/`에 남깁니다. 정책 담당은 기술 내용이 읽히는지, 기술 담당은 정책 내용의 사실관계가 맞는지 서로 검토합니다.
- 공개 저장소이므로 비밀번호, API 키, 개인정보는 올리지 않습니다.
